## Agreed operating story

The single product loop is:

**Find a specific capacity need → inspect record-level evidence → save a dated growth goal → choose the appropriate work → manage execution → observe readiness, acceptance, and completed work separately → decide what to standardize.**

The three legitimate responses to a gap remain alternatives to investigate:

- confirm suitable existing supply;
- help a known person complete verified readiness requirements; or
- source/re-engage supply when the verified current network cannot meet the need.

An unfilled request does not by itself prove recruiting is the remedy.

### Primary LAX scenario

- Fixed baseline: `2026-02-16T17:00:00Z`.
- Frozen schedule window: `[2026-02-23T08:00:00Z, 2026-03-02T08:00:00Z)`, equivalent to February 23–March 1 in `America/Los_Angeles`.
- Population: requests `req-lax-101` through `req-lax-110`; one remote realtime-deposition reporter slot each.
- Baseline: 10 requested, 6 valid accepted assignments, 2 distinct possible matches, 2 with no verified ready match, 0 goal additions, 0 first jobs for Avery/Rowan.
- Goal: two unique first-ever readiness events for LAX-owned first-time cases with verified realtime capability, after baseline and at or before `2026-02-23T17:00:00Z`. Baseline 0; target 2.
- Existing responses: separate acceptance events for requests 107/108 produce 8 confirmed, 0 possible, 2 no-ready-match.
- New readiness: Avery and Rowan independently satisfy readiness plus request-specific matching evidence, producing 8 confirmed, 2 possible, 0 no-ready-match and 2 goal additions.
- New acceptance: separate accepted assignments for 109/110 produce 10 confirmed while first-job count remains 0.
- Delivery: separate job outcomes produce 10 completed original-plan requests and 2 first jobs. At this point the records belong in plan review, not “upcoming work.”
- Mature onboarding check: Avery is late and Rowan is timely, so the two-person teaching slice is 1/2 within 14 days and 2 completed-to-date. It is not a program-effectiveness estimate.

Goal saves, task assignment/completion, outreach previews, coaching, program decisions, and process drafts cannot create readiness, acceptance, or job outcomes.

## Frozen data meanings

| Concept | Agreed grain and rule |
|---|---|
| Snapshot | `DemoSnapshotV2`, schema version 2, with seed/revision, base/current as-of timestamps, applied command IDs, applied scenario-event IDs, and current operational collections. Future feed events stay outside those collections until applied. |
| Reporter | One fictional network person across all service markets. Count distinct person IDs nationwide. A `Reporter` is never a `TeamMember`. |
| Acquisition case | One first-time acquisition case per person in v2. Owner market and primary source are fixed at entry. Re-engagement is work against the existing person, not a new identity/case. |
| Lifecycle | Append-only dated events with occurred/recorded times and reasons. Missing historical events remain unrecorded; migration never fabricates them. First job is derived from jobs. |
| Credential/capability/readiness | Separate evidence. Unknown, needs-information, verified, and not-demonstrated remain distinct. A readiness event requires its defined evidence but does not confer perpetual request eligibility. |
| Availability | Explicit bounded windows with status, scope, attendance, recorded time, expiry, and source. Expired or absent confirmation is unknown. Notes are not parsed into availability. |
| Demand request | One reporter slot with one canonical demand market, known/recorded time, scheduled interval, proceeding, attendance, capability and sample requirement version. It may exist without a reporter. |
| Assignment | Event history per request/reporter. Proposed/offered is not accepted. Latest valid state at the selected time determines commitment; one slot has at most one valid accepted reporter. |
| Job outcome | A separate observed result tied to a request, reporter, and accepted assignment. Completion cannot predate its prerequisites or declared work interval. |
| Internal work | One canonical `WorkItem` collection with ownership/status history and evidence. Recruiting/Programs call shared task actions; they do not keep private follow-up or partner-task copies. |
| Program enrollment | Explicit frozen membership with market/source at entry, eligibility evidence, group and optional process version. Outcomes join to lifecycle/jobs; v1 aggregate sample counts are not memberships. |
| Goal | Versioned `GoalRevision` with metric version, scope, baseline evidence, target, deadline, owner and supersession. Editing a goal never edits observations or prior evaluations. |
| Process | A versioned draft/review/limited-pilot record. Saving a process neither changes frozen cohorts nor enrolls other markets. |
| Command | Stable command ID, expected revision, actor, time, affected references and result. Replays are idempotent; stale revisions fail. |

All timestamps are stored in UTC. Requests display in market time. Reporting weeks use `America/Los_Angeles`. Calculations use an explicit `asOfAt`, snapshot revision, definition version and filter scope. Windows are half-open `[startAt, endAt)` unless a named metric explicitly declares an inclusive boundary, as M04 and M08 do.

## Frozen metric calculations

| ID | Population and calculation |
|---|---|
| M01 | Distinct non-canceled requests recorded by `asOfAt` with `startAt` in the selected schedule window. Live upcoming also excludes elapsed work; plan review retains frozen IDs and later outcomes. |
| M02 | M01 request IDs with exactly one valid accepted assignment at `asOfAt` / the same M01 IDs. Proposed, offered, canceled, conflicting, or ineligible records do not count. |
| M03 | Each unconfirmed complete-requirement request is exclusively `possible-match` when at least one candidate passes current readiness/verification, full-interval availability, service scope and commitment checks; otherwise `no-verified-ready-match`. Incomplete requirements use `requirements-unknown`. Candidate contention is disclosed. |
| M04 | Distinct first-ever readiness events after baseline and at/before the goal deadline for LAX-owned first-time cases with verified realtime capability at readiness. Returning/already-ready people are excluded. |
| M05 | Completed work is distinct completed outcome/request pairs. A first job is each reporter's globally earliest valid completion; later or cross-market work cannot create another first job. |
| M06 | Current stage is the latest valid known case event; first job is derived. Waiting/action queues include concrete unmet/overdue/unowned work, not completed cases or “routine progression.” |
| M07 | Funnel entry is unique cases first contacted in the selected entry window. Final 30-day conversion includes only fully observed cases and stage reaches within that horizon; recent cases remain “still being observed.” |
| M08 | First onboarding entry defines the cohort clock. Mature when `asOfAt >= entryAt + 14×24h`; denominator is all mature eligible entrants, numerator those whose earliest job completes from entry through the inclusive deadline. Immature entrants are separate; denominator zero yields null. |
| M09 | Source is fixed at acquisition entry. The same cohort supplies contacted/qualified/ready/first-job counts. Direct spend per first job is exact attributable spend / defined-horizon first jobs; zero outcomes reports spend without a $0 rate, and missing spend is unknown. |
| M10 | Recently working means a completion in the trailing 28 elapsed days, not availability. Weekly change compares distinct person sets at boundaries; first-time/returning use earlier global work history. All-market results are a union. |
| M11 | Open/overdue work uses current owned open tasks; completion credit stays with the completion actor. Output compares like role/unit targets. Quality is passed inspected items / inspected items. Coaching is an explicit record, never a score. |
| M12 | Program results join frozen enrollments to outcomes under one measurement horizon. Checklist pilot: earlier 6/20 (LAX 3/10, SFO 3/10); pilot 11/20 (LAX 6/10, SFO 5/10); target 50%. Nationwide totals use counts, not averaged percentages. |
| M13 | Weekly/goal review uses the goal's saved metric/baseline/scope/version and links actuals, open work, unknowns and decisions to evidence. Revisions never relabel historical success. |

Market bases remain explicit: recruiting outcomes use market fixed at case entry; fulfillment uses the request/job market; service-capability browsing uses declared service markets. Those totals can differ without contradiction.

## Evidence and navigation contract

Every important metric, signal, chart mark and table total must be rendered from one typed evidence bundle containing:

- metric and definition version, `asOfAt`, snapshot revision, unit, scope, filters and window;
- value plus numerator/denominator where applicable;
- distinct contributing references and join paths;
- ratio numerator/denominator member IDs;
- exclusions with reasons, unknown counts and limitations;
- a plain-language explanation generated from the same calculation; and
- an allowed navigation target with the exact affected-record filter.

References must resolve to human-readable source rows. Count evidence rows must reconcile to the count; ratio numerators must be a subset of denominator members; comparisons must expose both windows; spend joins must not multiply amounts. `Why this?` uses this bundle. `Open the work` carries the same IDs, filters, as-of time and definition version into the target view. Expected numbers in `scenario_contract.json` are test oracles only and cannot be rendered as runtime values.
